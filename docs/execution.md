# 执行已登记的检查操作

执行检查分工明确：registration 解释登记，FILEMAP 决定影响范围，routes 制定计划并核对工具，projects 执行操作、核对原始回执。它们共用已有执行器，不从目录、语言、Cargo 依赖或运行时扫描补出依赖。

## 执行计划和单项限制

FILEMAP v2 的 `execution_plans` 是从 `test:ID` 到 `{operations: [operation-ID, ...], timeout_seconds, output_limit_bytes}` 的映射。操作序列必须非空、有序、无重复，且包含唯一的测试执行方法；只有列出的操作才算前置。action、工具和原始参数仍归 projects／scripts。

可选 `operation_bounds` 为序列中具名操作提供完整 `{timeout_seconds, output_limit_bytes}`。没有覆盖项时继承计划默认值；映射省略或为空时，序列化计划身份保持原样。未知操作、缺少限制字段、非正上限或超过 64 MiB 的输出限制都会被拒绝。限制按计划明确登记，不按操作名称特判。

routes 把所选序列合成先后关系，共享操作只运行一次。在观察工具或启动操作前，先拒绝环和共享限制冲突。每个输出流最多 64 MiB；超时算基础设施失败，不能当作功能结果。同一共享操作在所有选中计划中必须有完全相同的最终限制，一方写了覆盖项不能替另一方解决冲突，也不取最大或最小值。

新增、修改、删除覆盖项都参与完整及按范围检查的变更影响。汇总只重建登记覆盖与最终限制，不执行业务操作。当前协调仓库启动计划的 `host.bootstrap-tests` 和 `host.bootstrap-real-consumer` 各为 900 秒／1048576 字节；distribution 与 release 集成计划仍用 600 秒默认值。旧完整宿主迁移计划已移除。执行计划通过不证明公开发布、真实 CI 验收或全面采用完整检查。

## 并发、优先级和共享资源

FILEMAP v2 可登记一份 `execution_scheduling`：

```json
{
  "max_running": 2,
  "priority": ["build.example", "test.example"],
  "resources": ["shared-inventory"],
  "claims": {
    "build.example": {"resources": [], "outputs": ["example/output/"]},
    "test.example": {"resources": ["shared-inventory"], "outputs": ["example/output/"]}
  }
}
```

`max_running` 是正的有限操作并发上限，与 CPU 数量和工具内部线程数无关。所有登记计划中的每个操作恰好有一条占用声明，资源和输出为空也要明确列空数组。资源名只能来自 `resources`；输出必须是现有 `config.artifacts` 的精确路径，旧按范围适配器使用其明确登记的产物路径。

声明缺失、未知、重复、歧义或无效时，在业务工具观察或启动前失败。不扫描语言、目录、调用图或测试。所有资源都独占，相同或嵌套的输出目录冲突；声明是否完整仍由登记者负责。

本仓不再声明整套测试共用的 `coordinator-fixture-producers` 占用。保留样本登记和修改排除归各次分配，独立生产者／报告处理会释放协调仓库的进入锁，单个套件不再全程占用每个样本存储。workflow／worktree 较窄的清单占用及精确输出占用仍保留。并发上限仍为二，内部测试线程、断言、租约期限和操作限制不变。

这次产品所有权与宿主调度政策一起修改，仍须标准变更和真实 CI 检查验证新的并发关系。协调登记和最终输出保留也已逐项存储；普通操作只访问目标及明确依赖。总耗时、存储和 CI 成本未知。原登记租约失败继续保留，尚未证明历史持锁者是谁。

`priority` 可选，按顺序列不同的已登记操作 ID。已就绪的列出操作先于未列出操作；未列出操作保持标准计划顺序。空或省略时保留原序列化身份和顺序。完整政策可以列当前单元未选操作，但优先级不选中操作，也不推断耗时或依赖。未知、空或重复 ID 在业务操作前失败。

只有 projects 调度 routes 的有向无环图。它按登记优先级、再按标准计划顺序选就绪操作；跳过冲突以便独立操作继续，启动前一次取得全部占用。前置仍在运行时等待，前置最终失败时只阻断其后续依赖。共享操作每次选中调用只跑一次。所有自有工作者都须等待结束，报告的执行／阻断记录保持标准顺序，不随完成先后变化。

原退出码、输出字节、超时和回执错误保持失败。未采用调度政策时串行执行，计划及身份保留旧格式；采用后完整声明进入计划身份，汇总从保留的候选登记重建并比较，不运行业务或版本命令。

并发上限、资源和优先级变化都会影响登记计划消费者。优先级顺序有实际含义，变化或移除须覆盖两端消费者；占用变化还影响两端明确冲突的消费者。输出声明变化保留明确消费者和负责人。移除或重新分配沿用两端记录与边的并集，不能为并发而删除必需检查。

## 进程所有权与描述符传递

Unix 进程记录可选 `ownership_fds`，保存执行器实际传递的使用凭据。`environment` 和 `environment_digest` 只描述业务输入，不包括保留变量 `CHRONO_PROCESS_FDS`。该变量由进程引擎根据实际继承／当前范围内的描述符设置，调用方不能用显式值替换。回执单独保留载体，避免把描述符分配当成业务环境漂移；没有载体时省略字段，原有记录仍可读取。

执行计划的业务工具绑定也排除这个变量。Rust 原生 CI 输入准备通过同一进程引擎转交继承描述符。Python bootstrap 和真实 Python 接口消费者仍须按登记方法转交同一描述符；只转环境变量不能维持内核锁。

引擎不修改已继承描述符及其标志，其他线程和后续原生子进程继续保留原凭据。引擎自己复制的描述符在子进程启动前保持 CLOEXEC；最后一个继承或自有描述符关闭时才释放内核租约。

Unix 引擎通过继承描述符 198／199／200 传递有上限的匿名启动树登记，不改变观察到的参数和业务环境。每次已知嵌套启动在 exec 前，把子进程和启动器的活跃身份交给首个引擎拥有并负责等待的唯一观察线程。macOS 使用内核退出与回收事件（`NOTE_EXIT`／`NOTE_REAP`），Linux 使用 pidfd 的退出与回收通知（`POLLIN`／`POLLHUP`），要求内核支持。退出和回收分别记录：直接启动器仍须真实等待自己的子进程；启动器已中断时，存活所有者须等登记的子进程回收后才能释放登记。

首次识别继承通道时，描述符 198 若带 `CLOEXEC`，则属于当前进程在 exec 后打开的资源，不作为继承树读取；父进程的该描述符及标志保持原样。未带该标志的通道仍须通过原字节、上下文和观察者校验，碰撞继续失败。独立子进程回归覆盖首次调用前占用该编号的本地 socket，以及无效继承 socket 的拒绝。

启动器被中断后无法运行析构。存活所有者只有取得两个精确身份的内核终态、并确认登记子树完成后，才可协调这次启动。PID 消失、发出 kill 或外层成功退出，都不能代替完成。启动代次避免延迟事件或旧继承上下文误用已复用位置。macOS 已有原生行为测试，Linux pidfd 仍需真实平台验证。

## 等待完成与超时

观察线程记录实际收到子进程内核退出事件的时间，时钟与 `Instant` 相同：Apple 使用 `CLOCK_UPTIME_RAW`，其他平台使用 `CLOCK_MONOTONIC`。监控器在启动原执行计时前固定证据截止时间。恢复执行时若已过期限，只有严格早于截止点的退出观察才允许立即探测一次子进程状态；实际已结束才保留子进程结果。观察缺失／过晚、时钟失败或探测仍未完成，一律超时，不再追加等待。

时间戳只说明退出不晚于观察时刻；观察线程自己延迟时，不能反推更早退出。取消、输出限制和所有权清理仍独立检查。私有映射身份区分布局版本，耦合的嵌套二进制须一起升级；继承所有者不兼容时失败，不能静默按新布局解释旧共享内存。

macOS／Linux 监控器阻塞在已有私有通知 socket 上，等待退出、等待完成、输出流、生命周期提示，或剩余执行期限。若及时收到内核退出观察、但期限内 `Child::try_wait` 仍未就绪，直接所有者把同一个 `Child` 交给唯一原生阻塞 `Child::wait` 线程。线程先发布实际状态或等待错误，再通知原 socket，无需额外提示或周期探测。期限后不启动等待线程。

监控器继续执行取消、输出和原期限限制；清理或栈展开时按需终止自有子进程，并在返回前等待线程结束。受控顺序回归使用真实内核退出事件、一次故意未就绪的探测，之后不再发送提示，要求得到真实结束状态和原输出。这只证明该状态转换，不证明某次真实 CI 超时的原因；新增等待线程成本未测。

唯一退出观察线程阻塞在登记的内核身份和现有启动登记 socket。取消、位置释放、观察器停止都通知同一 socket；已完成后代的移除在本轮事件处理内结束，再次进入阻塞。通知不代替真实子进程等待，也不证明成功。私有映射 v6 同时要求这些生命周期提示和独立回收标记，耦合嵌套程序须用同版本。

生命周期和身份事件通知保留的启动端点，共享观察器因此可以在真实树事件发生时唤醒兄弟监控器，不定期探测状态。这也覆盖排空条件里的进行中预留和明确后代。停止句柄共享已有描述符，不增加描述符预算，也不新增守护进程、轮询通道或执行时间。

监控失败时，在清理改变状态前一次保留启动身份、终止／取消标记、观察时间、父标记、有限位置数，以及实际／允许监控毫秒数。这些是分别读取的原子值，不是整树一致快照，也不作因果判断。它们可区分缺少退出观察与其他完成失败，无需探测进程、增加任务或改期限。

同一失败观察还保存启动树全部占用位置：位置／代次、父位置、记录 PID、终止、启动器终止和取消标记。最多 4096 个位置，只在清理前采集一次，不发现新进程，也不从 PID 猜存活。嵌套超时回归先核对保留的实际子进程身份和父子关系，再核对最终清理。

`completion_wait_blocks_without_periodic_status_probes` 在原生子进程中隔离一个引擎，真实业务子进程关闭两个输出流后等待 1500 ms，再退出 7。从启动后、关闭输出流的 socket 握手起，到引擎及观察器／读取线程真正结束，通过已有 `retention-test` 特性统计实际 `DirectChild::probe` 调用，要求大于零且少于 64。子进程只在统计窗口开启后开始原延迟。哈希、加载和所有权准备都在窗口前，握手使用阻塞 socket；系统上下文切换不再作为探测次数的代理。计数及读取只编译到测试特性，不增加生产路径状态、依赖、进程或 IO。

有限事件余量容纳 EOF／退出／加入通知，1500 ms 内的 2 ms／10 ms 周期探测应超过上限；变异验证须实际观察到失败。这项有限静默等待回归不证明全部任务所有权或宿主通知。已有超时、输出限制、挂起监控器、中断启动器、嵌套取消和描述符耗尽测试保留原义务；外部调用方句柄、通道丢失恢复和宿主完成通道仍按 SPEC §7.4 由调用方／宿主负责。

一次操作超时只取消自己的启动子树。嵌套引擎先终止进程组并回收子进程，外层再等待自己的子进程和输出线程。原执行期限后仍只有一秒清理余量；到余量中点仍未确认后代完成时，终止已登记的启动组，包括尚未退出的直接启动器，让被暂停的启动器所拥有的子进程能够被接管回收。剩余时间继续等待精确退出与回收通知，不能在发出 kill 后直接视作完成。即使最终完成，强制清理仍算失败；未知或不响应的完成也失败。执行上限不增加。

最多同时登记 4096 次启动；位置或内核描述符耗尽、描述符冲突、无法交接活跃身份，都在 exec 前明确失败。原生工具的普通后代留在启动组内；包装器若关闭继承描述符，就无法传递嵌套 runner 所有权。非 Unix 仍只清理直接子进程。不提供进程扫描、守护进程、任意未声明写入者保证或跨调用锁；调用方继续使用独立工作树及既有生命周期边界。

活跃身份登记失败时返回观察器实际内核 errno。子进程以有界、检查过的写入，在私有上下文描述符中发布固定的阶段／原因／errno。exec 前错误路径只用栈记录和原 OS 错误；父进程仅在启动失败后构造诊断文字。诊断缺失或不全不替代 errno，没有 OS errno 的所有者失败用 EINVAL。启动失败没有已执行进程回执，诊断不能编造退出或完成。

一秒交接／清理余量及执行期限不变。发送循环在同一交接余量内重试 EAGAIN、EINTR、ENOBUFS，耗尽后保留最后发送 errno。父诊断区分确认轮询超时与短读取。Linux pidfd 系统调用使用已有的明确 `libc::pid_t` ABI；编译成功不代表 Linux 运行行为已验证。

## 操作、输入与真实回执

registration 严格解释登记，FILEMAP 负责记录身份、目标和影响。计划变化指向测试和列出操作的定义记录。`operations`、`argv`、`version_argv` 保留顺序。`tool:ID`、`environment:NAME` 与 `input:ID` 一样，须有明确消费者边。只有走过 `test-execution` 才选完整规则测试；测试别名成为起点本身不选执行。构建／运行输入可以指向脚本或项目；Cargo 依赖、所有权关系或目录不自动产生边。

完整 FILEMAP 求值还比较两端经 registration 验证的保留实际环境。缺失／`null` 与空字符串不同，配置值先覆盖继承值再比较。变化只以已有 `environment:NAME` 为起点，沿两端明确边的并集传播，包括仅旧端存在的边。无连接或值未变时不选消费者。快照键未登记或实际事实矛盾时失败。`produce` 仍只读声明；`produce_with_inputs` 另读取已验证保留事实，两者共用记录比较、图传播和历史解释。

完整进程链是 registration → filemap → routes → projects。registration 发布绑定固定端点、登记摘要和上下文的不可变解释结果；filemap、routes 转交它，不重新加载未转换的历史登记。routes 核对 runner 在解析前采集的入口参数和 cwd。不同 cwd 下等价的绝对引用可接受，参数顺序、字面值和固定端点仍须符合登记方法。只展开整个参数恰好为 `{base}`／`{candidate}` 的项。

routes 输出 `chrono-execution-plan/v1`，绑定端点、登记、上下文、实际输入、观察到的调用和运行身份。每个选中工具只在声明环境中解析一次，保留绝对调用路径和 basename，实际观察文件字节、版本 stdout 和退出码。预期版本必须等于去掉末尾空白的实际 stdout。迁移的前次观察须验证后才能复用；每次启动前重核工具字节，不使用未登记 PATH 回退。

runner 进程引擎记录实际参数、标准 cwd、有效环境及摘要、stdin 摘要、可执行身份、原始 stdout／stderr 字节及摘要、退出和资源失败。两种检查协议都严格按 UTF-8／JSON 解码原 stdout；有损显示字符串只作诊断，任意操作字节仍保留。projects 据此生成回执。routes 比较回执／计划／方法／运行身份、参数、cwd、工具、输入／环境身份和输出摘要。

证明 action 可明确声明 `output_contract: {"version":"固定 Verus 版本","commit":"完整 Verus commit"}`。
该合同进入真实 Method、计划及回执身份，单独变更它也会进入两端操作比较。
routes 核完原回执后，由同源 Verus 判断同一原进程的参数、退出及一次解码的报告；
必须是完整 crate、非零 verified、零错误且版本／commit 精确匹配，才准入证明结果。
普通 action 不解析其业务 stdout；缺失或 null 合同表示普通操作，不按名称推断。
本地执行和离线 collection 共用这一比较，具体条件和明确外部解码合同见 [Verus 实施范围](verus.md#真实-verus-结果准入)。
采用新合同数据前，先通过现有 bootstrap 部署能读取该字段的生命周期所有者；旧严格读取器会在构建前拒绝。

回执缺失或矛盾会失败；核回执不能把非零退出、输出超限或超时变成成功。失败后独立分支可以继续，依赖操作标为阻断。已选、已执行、被阻断、已移除和替代义务分别记录。操作前后都检查候选未提交改动。

Unix 信号终止在 `failure` 中记录信号号和子 PID，保留旧 `exit_code: -1` 及原输出。准备后和显式旧入口的失败报告保留实际启动进程。传输先报告进程失败，再尝试解码响应 JSON。普通数字退出不变；引擎取消、超时、输出超限保留原因，不能被清理信号重新分类。信号观察不说明谁发送或为何发送。

projects 核对受影响项目／测试、脚本／测试是否互相且独占配对、是否明确登记执行边、文件归属，以及生成目录隔离。生产项目须有登记文件和一个专属测试；脚本保留明确路径及配对。不要求 manifest、锁文件、源码根或生成输出。可选旧 manifest／lockfile 只是归该项目所有的普通引用，root 不推断语言或输出。不同所有者共享或嵌套输出会失败，登记输入不能位于生成输出排除目录内。产物记录变化也指向两端明确负责人，不能只改输出就变成无工作。

action 名可为任意明确非空值，每项绑定全局唯一操作；测试 `execute` 仍是执行入口，FILEMAP 计划提供有序前置。manifest、扩展名、import 或目录发现都不改变归属、依赖和选测。

本仓测试项目由实际 `cargo test` 操作编译并执行，不另外登记没有当前调用方的 `cargo check` 或 `cargo build --tests`。生产构建、原行为测试、格式操作和同源 Verus 证明各保留其实际入口。缓存登记中的 `check.*` 是缓存 ID，生产者仍明确绑定 build／test 操作，不能把同名缓存误当成 Cargo check 的调用方。

只登记自身、未接入计划或操作说明的临时过滤测试动作已经移除；测试本体继续由原未过滤操作或现役分组执行。macOS 27 政策也不再单独登记没有 action、输入绑定或 FILEMAP 使用方的 linker 工具；真实编译归原 Cargo 操作。

语言检查由另选适配器承担。[chrono-judge-cargo](cargo-projects.md) 通过宿主明确政策保留 workspace 和 TOML 路径依赖检查。完整协议样本验证其失败阻止操作、纯文档变化不重判无关 Cargo 历史。通用样本覆盖无 manifest 项目、普通旧文件、自定义 action 和任意位置。真实 Go／TS／mix 声明可由通用格式和配对消费者接受，但这不证明 SDK 输入完整或全面启用检查。

context 可以指向根目录相对的 `retained_inputs` JSON 文件。`base` 和 `candidate` 各含 `commit`、`environment`、`files`。继承环境变量映射到字符串（可为空）或表示缺失的 `null`。每个 `files[ID]` 要么含字节数组 `bytes`，要么精确为引用保留状态内容的 `{blob, sha256, length}`。[输入快照工具](inputs.md)可采集并传输，不必内嵌大文件。runner 传递快照元数据。

普通完整检查核验两端每个已声明外部文件的保留摘要及当前候选磁盘字节；完整单元检查按 registration／input 的明确前置范围投影，包括共享和检查规则输入，不要求无关实时 SDK 文件。汇总核验原 blob 和各原单元输入投影，不读取当前业务输入。全局结构／引用校验仍保留，传入未知或畸形输入仍失败。

registration 比较候选环境和 runner 观察，不从当前磁盘重建旧字节。报告发布输入身份与长度，快照仍作证据。解释器、委托工具链、配置和样本字节须登记为实际输入；声明和哈希不能证明没有未披露输入。本仓仍为 `proposed`，且明确输入不完整。

## Full v3 单元执行和汇总

完整登记可选择 `execution_units`：将每个候选执行计划恰好分配一次，列出重复共享操作，设置有限的清单／报告字节上限，并给各单元和完整汇总报告不同的状态路径。分配为空或未知、路径重叠、与标准报告位置冲突、限制无效时，registration 在业务启动前拒绝。分配和选操作的辅助逻辑与按范围入口共用；v1／v2 和不分单元的完整请求保留原协议格式与行为。

`--unit ID` 仍运行全部七个检查程序。routes 先验证全局变更选测、替代、前置和操作顺序，再只把该单元选中的完整计划交给 projects。集成和交付运行都核对单元本地回执及适用的上下文／分支要求；依赖整体完成的迁移、替代、移除和证明判断留到汇总。

报告记录 `global_selected`、`own`、`assigned_elsewhere`、`required_units`、`not_required`，以及从声明生成的全局图。完整报告和证明消费者拒绝把单元贡献报告当作整体完成。

所选报告保留一份封存的首个检查请求模板。runner 共用的 `judge_request` 根据模板、配置 DAG 和精确前置记录重建各原始 stdin，并核对实际摘要；前置观察不再内嵌请求。

当前准备流程明确选择 `chrono-retained-process/v2`：每条流保存 zlib 压缩十六进制、原长度和 SHA-256。有界解压器拒绝尾随、截断、损坏或相互冲突的流表示。原参数、cwd、run ID、回执身份、退出和错误不变，Git 观察使用同一编码。历史内嵌格式和 `chrono-retained-process/v1` 十六进制仍可读取；没有请求标记时保留历史完整内嵌／scoped v1 的 stdin 构造，不改原件。

完整分单元报告发布、projects 汇总／完成、汇总工作流证明，都把序列化元数据加 v2 原 stdout／stderr 长度计入已有 `report_bytes`。压缩不扩大原始流预算。历史内嵌／v1 仍按原序列化字节计费，之后仍核原字节与摘要。

显式 `ProcessEvidence` 消费者使用同一进程引擎，保留实际读到的字节和原子启动身份。外层终止后若没有结束证据，结果仍未知；启动记录发布成功不算成功回执。启动后的发布失败仍体现在真实 `ProcessResult` 中，保留已读有界字节、剩余流读取、退出码和身份。启动记录发布失败时，诊断保留原启动记录及两个 PID；启动前发布失败则不启动子进程。

按范围检查的输出流发布错误携带 `E_PROCESS_EVIDENCE` JSON 诊断，包含无损进程信息及已成功保留的 stdout 引用；二次编码失败则回退到原内嵌回执。部分文件或发布失败不能成为成功报告。Git 事实明确按[事实 v2](git-facts.md)区分版本；进程编码兼容不代表 v1 facts 请求兼容。参与检查失败时，准备状态保留原进程，报告返回地址／摘要，不同时嵌入两种流表示。这些是证据传输和保护要求，不代表 SPEC §10.1 自动移除已完成。

### 外部原件如何随报告传输

有地址的上下文、保留快照／blob 和引用证据，使用原逻辑键下的外部 `chrono-retained-blob/v1` 描述符 `{schema, storage, sha256, length}`。`storage` 明确指向所选上传根下的状态路径。暂存按有限缓冲计算摘要和复制，相同原字节去重；原 `{sha256, length, hex}` 内嵌格式仍可读取。

JSON 报告和进程流保持既有限制，外部业务 blob 不占内嵌十六进制预算。JSON／进程解析仍限 64 MiB，输入身份和传输验证则流式读取大文件。不可变运行记录保留早先尝试，登记单元路径标识新尝试。

这种可转移的完整依赖集合只用于单元和汇总。普通完整检查保留本地 blob 引用，由 registration 流式核对原身份和候选身份，允许输入大于可转移报告上限。畸形、缺失或改变的 blob 仍由输入模块在业务前拒绝；不分单元的报告不把这些文件内嵌为可转移字节。

汇总导入重新暂存每个声明的外部原件，保持单元报告字节不变。完成记录明确映射原存储地址到导入描述符，最终报告在汇总上传根下保留全部嵌套依赖；交付按绑定的传输解析。映射缺失、嵌套字节丢失、截断或身份冲突都会被拒绝。失败运行保留原失败，并在 `artifact_failures`、`unresolved./artifacts` 报告不可用原件。

### 报告发布前的一致性核对

runner 在组装完整报告前，独立核对执行循环返回的记录：

- 用另一遍拓扑遍历重建登记的绑定 DAG，核对各请求和 stdin 摘要。
- 按绑定核对可执行文件、argv、cwd 和环境回执，按实际退出核对响应身份、状态和问题列表。
- 被阻断记录须指出失败的已登记前置，或重现请求构造失败。
- 成功响应字节须匹配原进程 stdout；保留流的文本和摘要须匹配原字节。
- 若保留进程其实含有效协议响应，或进程失败证据不符，则拒绝传输失败记录。
- 启动前错误须有预期请求身份，且没有进程、响应、退出和 stdin 证据。
- 重新计算汇总状态。

任一矛盾都报 `E_SELF_DIAGNOSTIC` 并阻止发布。这只检查已声明输入的一致性，不发现依赖、不验证宿主输入完整，也不证明检查程序的业务结论正确。

### 离线汇总

`--collect MANIFEST` 使用同一七程序入口，读取有上限的 `chrono-full-collection/v1` 清单，每行含 `unit`、`path`、`sha256`。runner 和七程序身份来自当前绑定调用及候选登记。routes 只规划完整声明图，不观察业务工具，包括版本命令。

projects 对每个必需单元核验一次，也核验所有额外提供的非必需单元。它从原检查响应和成功进程推导成功／警告，核对 DAG／stdin 一致性，重建声明输入、入口、工具／版本要求、计划／顺序／前置／限制、义务分组和回执。保留回执还须满足每条输出流限制；回执自身摘要不足以替代这些比较。

原仓库根可以不可用，原证据只能来自明确声明和传来的字节。外部输入位置、环境含义和原进程坐标保持精确。runner 的 host-root 别名按保留的原调用及既有实时路径解析核对，汇总不重新打开或改写旧根。

历史转换在汇总时读取原解码器观察。当前 registration 比较固定原字节、候选解码器、声明工具／版本／输入和原成功进程，不启动解码器；每个提供单元的转换都要核对。声明的工具、输入、环境节点可通过明确 `runtime-input`／`judge-trigger` 边到达检查消费者。单元分配和共享操作变化，复用计划变化的同一登记目标。

projects 产生有类型的 `chrono-collected-completion/v1`，含与来源关联的覆盖情况，不伪造汇总器自己的业务执行记录。每份原报告按内容摘要保存。最终汇总报告包含原报告、全部有地址证据、清单和实际汇总进程。

workflow 对直接完成或验证后的汇总完成应用同一完整迁移／集成政策。交付核对真实最终 pass／warn 报告、实际 workflow 输出和原始来源依赖；临时、截断、失败或仅单元贡献证据都会被拒绝。单元／汇总路径不能与标准报告、配置的证明／上下文目的、保留输入产物或不可变证据重叠。报告和清单按登记上限执行，最多 64 MiB；过大就失败，不静默截断。

核心已提供明确单元执行和离线汇总；CI 模块通过明确 full-context／上传映射提供工作流生成和自动产物传输。完整宿主真实 CI 启用、bootstrap／输入齐全、provider 实际采用和公开发布仍待完成，不能由这些检查推导普遍同判或运行提速。

专属 workflow 消费者测试包含两组真实独立 Rust 生产／测试配对、共享前置、失败单元及选择性重试、原根和业务工具不可用时的离线汇总、含义变异、跨单元替代／迁移与联合移除、空汇总，以及汇总集成后交付。FILEMAP 和 runner 消费者也核对分配变更及完整报告入口拒绝贡献报告。

## 首次文件清单检查

无父提交可在 `.chrono-harness/` 下明确使用独立配置：

```json
{
  "schema": "chrono-initial-check/v1",
  "host_config": ".chrono-harness/config.json",
  "timeout_seconds": 30,
  "stdout_limit_bytes": 1048576,
  "judges": [{
    "id": "initial-registration",
    "executable": ".chrono-harness/bin/chrono-judge-registration",
    "version": "0.1.0",
    "sha256": "<已安装候选可执行文件的 SHA-256>",
    "argv": ["--protocol", "chrono-initial-judge/v1"],
    "selector": "every-initial",
    "modes": ["inventory"],
    "after": []
  }]
}
```

配置本身也要登记到 FILEMAP，提交完整初始清单，再与普通变更 `profile` 一起绑定到 schema4 的 `canonical_check.initial_profile`。独立 v4 provider 明确登记同一清单路径及生成配置。本地与 CI 采用同一入口：

```sh
.chrono-harness/bin/chrono-harness check
```

登记的输入模块只依据真实 Git 拓扑或原生事件证据，为无父候选选择初始清单；非根提交仍走普通变更配置，须有登记基线。两配置路径和摘要、真实短入口、候选配置及生产原件继续绑定。缺少初始绑定就报错，不回退。空业务清单不需要单元；已有非空按范围单元初始化保留独立明确要求。旧登记保留原初始 CLI 要求，见[独立首次采用](ci.md#standalone-initial-host-transition)。

初始配置拒绝 `--base` 和 `--context`。runner 读取实际提交头，非根提交不能因浅历史或 Git replacement 隐藏父提交而进入。共用不可变 Git 事实禁用替换对象，按范围 CI 和事件准备复用同一父提交读取器。

各检查程序使用完整宿主配置的明确环境，按既有 Git 环境身份排除 schema4 声明的仅获取阶段凭据。`after` 构成明确 DAG，前置失败只阻断依赖。路径、语言和检查 ID 不选择额外检查；原进程限制、字节摘要、严格 JSON、请求身份和状态／退出精确核对继续生效。参数可展开 `{candidate}`，使用 `{base}` 则报错。

请求为 `chrono-initial-judge/v1`，模式 `inventory`，只有候选端，没有 base 或 DELTA。`profile_sha256` 绑定配置原字节；`registry_digest` 是五份候选登记路径到解析 JSON 值的 JCS 映射之 SHA-256。请求还绑定配置路径、工作树、实际 runner、观察和明确前置响应。响应字段沿用普通结构，但使用此协议身份；没有变更路径集合，所以问题引用必须是 JSON 指针。

默认 registration 初始检查核对 proposed 登记格式、全部当前引用和文件成员、实际配置／可执行绑定、固定候选字节，以及工作树干净状态，包括被忽略改动和不支持的索引标志。它在明确初始范围内复用普通规则，没有历史端点。默认拒绝 active／enabled 登记：之后启用仍须真实变更及既有准备／集成义务。

初始清单检查不执行项目测试、不证明配对含义或工具链／输入完整，也不替代另外六个检查程序。其他清单检查程序／脚本要明确绑定。

`chrono-initial-report/v1` 写 `scope: initial-inventory`、`base: null`、`delta: null`、`previous_enforcement: none`、`governance: not-evaluated`。`status: complete` 表示配置清单检查成功结束，退出 0；`failed`、`error` 保留非零。各响应保留 pass／warn／fail／error 和原进程回执。

报告按内容身份保留在所选真实 CI 上传根，本地则放 `.chrono-harness/state/`，最新副本为 `initial-report.json`。短控制台输出指向不可变原件，旧入口输出 JSON。不改登记状态或输入声明。完整 bootstrap 来源、启用、兼容公开安装和真实初始事件验收仍待完成；生成和本地／原生生产者样本测试不能证明完整同判。

## 历史格式转换与按范围 CI

严格 v1 读取器拒绝 v2。候选读取器把 v1 结构保留为历史数据，不编造计划。内置宿主解码配置是 `chrono-ci-check/v1` 加 FILEMAP v1，登记在 workflow v2 的 `historical_profiles`。每项点名原配置路径、候选脚本及专属测试、精确的畸形旧记录、身份映射和有限歧义修复。已有 `migrations`、`retirements` 保留迁移与替代事实。config 还支持两端明确的 v2 存在／缺失声明，见[输入快照](inputs.md)；projects 支持 v1／v2，judges 使用 v1。

workflow v3 新增版本选择：`from_versions` 和 `to_versions` 各包含 `config`、`filemap`、`projects`、`judges`、`workflow` 五个正整数。前后映射必须不同，并精确匹配固定端点。其余字段为 `id`、`script`、`test`、`mappings`、`legacy_records`、`ambiguities`。旧标记配置仍按原含义读取。匹配超过一个就失败，未匹配版本配置则不运行解码器；每个变化格式仍须当前迁移声明。只有实际数据转换才要求转换器及已执行测试；只更新当前规则时不写这两个字段，也不增加历史兼容义务。

选中的候选脚本接收 `chrono-historical-decode/v2`，含 `config_path`、`original`、`original_bytes`、`candidate`、`profile`，返回历史解释 `values`、保留旧定义 `historical` 及声明的 `mappings`。历史 `config` 必须仍等于原值，旧输入快照保留原格式与摘要。

该接口支持宿主登记的 v1→v2 config 转换／兼容检查，不给旧快照换标签，也不把未绑定的 v1 摘要当作缺失。运行时不替宿主生成转换算法。专属登记测试必须真实执行且通过，无关测试配对不能替代。未变的 v3 宿主在纯文档变更时不重做版本迁移。

使用原生配置选择项时，registration 结果为 `chrono-registration-view/v2`，用 `config_bindings` 保存两端入口／实际配置路径。解码器输入为 `chrono-historical-decode/v3`，新增同一绑定，并按原路径保留 selector 与目标值。身份或原字节缺失／替换时拒绝；后续读取器也按解释结果核对保留解码输入的格式、标准入口和两端绑定。

inputs 消费者会实际执行所选 workflow v1→v3 解码器及专属兼容测试；即使候选已没有旧目标，历史 selector／目标仍保留原值。直接 v1／v2 解码要求不变。

当前本仓直接使用现役 FILEMAP 计划和项目 action。固定历史按范围宿主解码器、宿主／工具样本、对象获取辅助和迁移测试程序都已移除。当前 projects 验证使用原始未过滤专属 action。明确 workflow 移除声明把旧迁移组映射到该 action，但不声称仍保留已经退出支持的历史断言。

按范围 CI 与完整 workflow 共用 registration 的测试移除结构检查。不设替代项时，必须移除定义测试的项目／脚本及配对生产者，并明确声明生产者也无替代移除。分组别名通过保留的定义所有者解析。替代项必须解析成唯一当前测试，其现计划必须实际通过；移除声明或仅清单汇总都不能批准未执行替代。

单元汇总通过原回执核验全部全局选中的当前操作。`removed`、`retirement_context` 保留已移除身份、旧定义和声明成本，空成本仍未知。仍存测试可以更新方法，不必永久保留已删除操作。

**产品与政策曾同步修改：**按范围 CI 和独立 routes 不再要求保留每项旧操作，本仓也明确移除过时解码器与迁移组。结构拒绝和当前替代项真实执行仍保留。验证范围包括共用结构边界、真实按范围成功／失败、独立替代执行、既有 workflow 消费者，以及受影响两端的标准／真实 CI 变更检查。总验证成本未测。

通用转换和迁移接口使用合成、自包含 workflow 样本，验证明确映射、有序操作、实际转换回执和失败输入，不获取历史仓库，也不提供生产兼容路径。当前演进和移除证明归[工作流检查](workflow.md)。

专属 routes／projects 测试覆盖真实进程、保留输入、含空格宿主路径、不同 cwd、字面特殊字符／空／换行参数、顺序／去重、拒绝用例及真实退出／输出／副作用。单工作者检查不算独立评审、真实 CI 或落地证据。同一影响结果的登记成本由独立[成本检查](costs.md)负责。

## 一个测试项目中的明确分组

测试项目可增加 `test_groups`，将不带 `test:` 前缀的测试 ID 后缀映射到同记录的 action 键，映射必须包含原项目 ID。省略时继续使用 `execute` 别名；脚本保留原要求。例如 `{"suite":"core","detail":"detail"}` 把 `test:suite`、`test:detail` 分别绑定到同一专属项目的两项 action。

registration 为完整和按范围消费者解析身份、定义项目和最终操作。空／重复绑定、本地 action 缺失、在生产项目／脚本上放分组映射，以及明确身份冲突都会失败。原有歧义别名继续可见，按本次变更范围判断。

各组独立登记 FILEMAP 计划、成本和依赖边，生产者仍保留原专属测试配对。配对校验要求生产者到每组都有明确执行边。登记变化在两端保留全部组身份为记录目标，不从名字、路径或 Cargo 过滤器猜依赖。计划必须含绑定的最终 action。原始未过滤 action 可以供发布使用，而不成为当前独立单元计划。

## 声明测试语言

projects v2 要求每个项目和独立脚本都有非空 `language`，包括专属测试。projects 只比较受影响的生产／测试配对：字面标识相同通过，唯一额外允许的配对是生产 `shell`、测试 `python`。宿主显式使用这两个保留名称；其他语言 ID 按原样比较，不按路径、扩展名、工具或扫描推断／标准化。

v2 缺少语言声明会在结构检查失败，受影响配对不匹配则在业务前报 `E_TEST_LANGUAGE`。v1 保留原要求，拒绝新字段。语言编辑发生在原项目／脚本记录，因此两端影响覆盖仅元数据变化及已有明确测试边；未受影响的历史含义错误不重新判断。

这只验证声明的配对语言，不能证明实际内容或不存在隐藏跨语言辅助。已有 routes／回执仍把实际操作绑定到登记参数和工具。完整宿主采用和外语测试逻辑迁移仍须另行完成。
