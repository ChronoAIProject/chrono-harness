# AI 的 PR 工具

目标是让 AI 用一次命令打开 PR、查询固定提交的检查结果，或等待检查完成。独立 Rust 项目 `pr` 维护 `chrono-pr`，`pr-tests` 验证真实 CLI 和子进程。进程执行、时限、输出上限和子孙进程回收复用 runner；GitHub 认证和等待使用现有 `gh`，不另建凭据代理、后台任务或集中状态账本。每次操作的原件由现有输出保留所有者保护。

设计参考固定版本 [trureturing 的 PR 入口](https://github.com/the-omega-institute/trureturing/blob/481b9d7c46c8ef94b34842eb888d1ac254b2349f/tools/scripts/pr.sh)：显式远端分支、head SHA、结构化结果、有界请求和等待。参考仓库只读，其政策、门数、语言工具链和认证代理不属于本产品。

## 构建与调用

从本仓根目录执行登记的 `build.pr`：

```sh
cargo build --locked --manifest-path crates/pr/Cargo.toml
```

当前源码入口为 `crates/pr/target/debug/chrono-pr`。发布计划已登记 Linux x86_64 和 macOS arm64 的 `chrono-pr`，通过[现有安装入口](distribution.md#一键安装)选择工具；所选固定发布的清单必须实际包含它，候选登记不表示已经公开发布或安装验收。

本宿主将 `crates/pr/target/` 声明为 `finish-dispose`，因为构建完成后的 PR 命令仍需该执行物。普通 `build.pr` 使用结束后保留目录，调用方核对全部 PR 操作完成再走正式 finish；检出继续复用时，显式维护也保留该目录；实际检出处置仍须排除使用方。使用方须已有能访问目标仓库的 GitHub CLI。工具沿用 gh 的原生认证，不申请额外权限。`.chrono-harness/pr.json` 使用 `chrono-pr-config/v2`，显式设置仓库、目标分支、检查名称、gh 程序、资源上限，以及 `state_directory`／`state_producer`。本宿主采用 `.chrono-harness/state/pr-operations` 和 retention.json 登记的 `pr-original`。宿主必须采用现役 retention/v2，登记 `pr-original` 的操作目录范围；缺失时不派发 gh。进程原件由同一个操作目录所有者保护，无需单独登记 `check-original`。配置与结果均只接受当前格式。其他宿主提供自己的同格式文件；默认读取 `--host-root` 下的 `.chrono-harness/pr.json`，也可用 `--config` 指定。

```sh
crates/pr/target/debug/chrono-pr pr-open \
  --head integration/my-change --head-sha <40位提交SHA> \
  --title '添加功能' --body-file /path/to/body.md
crates/pr/target/debug/chrono-pr pr-status --pr 123 --head-sha <40位提交SHA>
crates/pr/target/debug/chrono-pr pr-watch --pr 123 --head-sha <40位提交SHA>
```

所有命令支持 `--host-root`、`--config`；`pr-open` 可加 `--draft`。打开前，调用方先保存、检查并推送候选。工具只支持同仓库分支，先核远端分支 SHA，再查找相同 head／base 的现存打开 PR；唯一匹配则复用，无匹配才创建。标题和正文按字面值传给 gh，正文通过 stdin 传输。创建后重新读取 PR，核对仓库、编号、base、分支和 SHA。并发调用或网络中断不保证事务；创建失败或回读失败保留未知结果和原回执。恢复时先核原操作、远端 PR 与固定身份；再次打开虽然会先查询现存打开 PR，但空列表不证明旧创建没有发生，不能据此盲目重复创建。跨中断的自动恢复尚未实现。

`pr-status` 可加 `--continue-operation <前次结果的operation>`，在一次只读查询中接续已有操作。工具先取得原件读取保护，核原生产者封存、物理身份、配置、仓库、PR 和固定 head，再核封存的对象保管状态、每份调用回执及其 stdout／stderr／launch 原件的实际字节、摘要和物理身份；原本地调用须已有完整结果，创建副作用须已核实。新操作独立保存旧结果的精确引用和新结果，不重写旧结果、不重做创建或等待。当前成功查询封存且身份核对通过后，沿原保留所有者补完封存后中断的旧操作保管交接，再结清明确接续的已返回操作。已完成交接可重入；待交接的操作仍要求受保护的封存结果。新记录不建立永久依赖链；旧原件在期限后可能不可取得，缺失不反推旧结果。缺失、部分写入、未封存、活生产者或身份变化均在派发前拒绝。新查询的认证失败是已结束的命令，不能结束旧 OPEN 对象；新发布失败继续保留未知操作。此参数只用于 `pr-status`，不启动第二等待通道。

`pr-status` 一次读取 PR 和指定提交的检查。`pr-watch` 先读取一次；仍待完成时，只启动一个原生 `gh pr checks --watch --interval 60` 等待通道，结束后回读同一 PR／提交。等待程序退出本身不产生通过状态。等待覆盖 gh 看到的全部检查，最终判定只消费配置列出的必需检查；原生通道未见到检查、提前返回或中断时，不额外轮询，结果保持 pending／unknown。超时停止并加入本工具的本地子进程，远端 CI 仍可继续；报告保留 PR、SHA 和原始回执，供后续查询。

等待总期限也包含首次 API 查询。该查询未成功返回时，不能建立已观察的 head 或 pending 状态，超时返回 `unknown`／退出 2；取得有效 pending 观察后，期限耗尽才返回 `pending`／退出 3。回归保留原一秒期限和原生等待输入，另以首次查询的超时输入核对这个边界；实际派发以生产者的原调用回执为准，替身自身的日志可能尚未写完。替身将完整 JSON 行序列化后一次写入，保留 argv／stdin 合同；这不保证任意中断下日志完整，也不代替生产者回执。

## JSON 和退出码

stdout 恰为一份 `chrono-pr-result/v2` JSON，帮助信息除外。结果含 command、repository、base、pr、expected_head、observed_head、outcome、checks、error 和 receipts，并给出 `operation`、`continued_operation`、`operation_state`、`command_exit_code`、`pr_state`、`merge_commit` 和更新时间。每条回执保存实际 argv、执行物摘要、PID、退出／signal、失败、流完整性和 stdout／stderr／launch 原件的路径、长度及摘要；正常结果不再内嵌两套流字节。消费者读取原件并核摘要。原件写入失败时，stdout 退回实际已取得的内嵌字节并明确报告 `storage_error`，退出 2；该输出不声称已持久保存。不保存子进程环境值或凭据，调用意图只保留环境摘要。

CLI 复用 runner 已有的宿主日志入口，按明确的 `--host-root` 读取 `.chrono-harness/logging.json`；未采用时沿用原输出。采用后，有限日志保存命令开始、真实返回码和已有进程事件，stdout 的 JSON 与业务 stderr 仍走原出口。日志政策或发布失败沿现有日志入口报错，不伪装为业务成功。时间观察不能代替原进程结果，也不能证明诊断本身没有开销。

**产品与宿主登记同时修改：**PR CLI 接入现有日志政策，FILEMAP 增加对应使用关系；Rust 用例在原 `test.pr-tests` 中核查询、原生等待后回读和 API 失败的结果、原调用次数、有限日志及凭据不泄露。原测试、线程和五秒业务时限保留，不增加诊断专用执行入口；实际超时原因和新增 IO 成本仍须由本轮原件核实。

| 退出码 | outcome | 含义 |
| --- | --- | --- |
| 0 | opened、existing | PR 已创建或已复用，身份回读通过；不代表检查通过 |
| 0 | passed | 所有登记必需检查成功，PR head 与期望 SHA 相同 |
| 1 | failed、closed | 必需检查失败，或 PR 已关闭且未合并 |
| 2 | unknown | 参数、配置、API、协议、输出上限或本地等待错误 |
| 3 | pending | 必需检查缺失、尚在运行或等待超时，不能判定成功 |
| 4 | stale | PR／远端分支 head 已变化，当前结果不能用于期望 SHA |

必需检查集合须非空。只将 `SUCCESS` 视作成功；取消、失败、超时、需人工操作、过期和启动失败均失败，neutral／skipped 也不满足必需成功。缺项保持 pending。未知状态、同名歧义、错误仓库／编号／提交和截断的检查集合明确报错。API 的分页上限为 100 项，超出时保持 unknown，不把可见子集当完整集合。合并后的检查成功仍只表示该提交通过检查，不能证明落地提交、发布或工作树清理。

## 本地操作原件与当前边界

每次调用在登记目录下取得独立操作地址。原件保留所有者先登记输出 intent、绑定物理目录并保护恢复使用方；工具再写不可变的 `config.json`、`intent.json`。每次 gh 调用前保存实际 argv、输入原件、执行物／环境摘要、精确时限、输出上限、时间，以及 `process_originals` 的三个明确地址；这些写入失败就不启动 gh。没有实际句柄或结果时字段为 null。现有 runner 在运行中保存 `<operation>/call-N.stdout`、`<operation>/call-N.stderr` 和 `<operation>/call-N.launch.json`，作为操作目录的成员。PR 明确借用现有目录发布能力；runner 复用其路径、节点和字节上限检查，预留两条流的原输出上限，不猜测父目录所有者。启动原件使用 `chrono-process-launch/v2`，绑定实际 PID、argv、执行物、输入及环境摘要，禁止保存环境值；内存执行结果仍保留实际环境，供现役绑定核对。流文件随原读取器写入已经取得的有界字节；launch 和部分流均不表示进程结束。进程返回后，PR 核对原件身份、字节、摘要和启动绑定，直接引用原件，写 `call-N.result.json`，最后发布 `result.json`。文件及所在目录同步后才继续派发。缺失、部分写入或未完成保留发布均不算终态。

`operation_state=completed` 表示本地调用已返回并收取本次子进程的实际退出码或终态 signal，已派发的创建副作用也须有匹配回读。等待失败、没有原退出结果时，操作继续为 unknown；已取得的输出和启动记录保留，后续 PR 查询不结清该原任务。实际命令退出码另存；`pr_state=OPEN` 仍是活跃 PR。MERGED 必须带真实有效的 `mergeCommit.oid`，它只是远端观察，不证明实际落地树／发布已验收。原结果、PR 状态和存储发布状态分开；最后的保留封存或引用释放失败也退出 2，先前已写出的业务结果继续作为原件保护，不把它当完整成功。

PR 对象按“仓库＋PR 编号”保管；head、base 和配置属于本次查询绑定。每次实际查询先在现有逐对象消费者记录中预约递增序号，绑定真实操作输出，并写持久意图。该记录只包含当前有效 OPEN 观察和仍有未结查询的操作；初始私有恢复引用在交接后释放。不同 PR 不争用同一份记录，无总清单准入、全库扫描、后台服务或按时间排序。

进程原件随操作目录一起封存。命令返回、结果及 `object-state.json` 封存后，最后一个有效观察按查询预约次序推进当前对象保管：较晚返回的旧查询不覆盖较新的观察；watch 的最终回读独立预约，初始 OPEN 后的 API 失败不抹去有效对象事实。新有效 OPEN 替换旧当前记录，实际 CLOSED／MERGED 释放对象保管，即使本次固定 head 已过期。这里的对象事实不产生旧提交的检查通过结论。

操作发布能力保护运行中的全部成员；接续只取得父操作的读取保护，再逐份核对封存清单中的精确路径、物理身份、长度和摘要。删除三份原件各自的发布记录、读取保护、外部依赖和输入交接；同一树内的保留与回收由一个现有所有者负责。独立外部使用方仍须持有读取保护；未返回或部分写入仍保持未知。完整运行和存储成本未测。

完整封存的只读失败命令也可结清，只释放自身待结查询，不结束仍 OPEN 的对象。未返回进程、结果／原件发布失败，以及实际创建后尚未核实的副作用继续保留，独立成功查询不能结清它们。真实外部使用方和读取凭据继续保护旧原件。已释放原件沿现有 diagnostic 窗口及 retention 维护入口滚出；空对象记录按现有 metadata 窗口回收。本宿主两个窗口均为 86400 秒，输出和每轮节点／字节／时间上限不变。

**这一批是 §7.5 的局部实现。** gh 尚未返回时已保留真实启动句柄和部分流；外层中断的 Rust 验收核实际 live 原件、缺失终态与后续维护保留。中断后的原操作仍是 unknown，不能从 PID 缺失、旧 intent 或新查询推定结束；没有完整进程结果时不会发布已完成操作。显式接续只覆盖原本地调用已返回且结果封存的记录；尚无完整结果的旧 unknown 仍受保护，不能靠新查询证明旧进程结束。同一 PR 的已完成独立查询已由当前保管替换及有限窗口回收；不扫描旧版本历史，也不把仍未知的任务当作终结。保留政策迁移、跨中断自动接续收取原结果和全部工具采用仍未完成。参数／配置／留存入口在有效 state 建立前失败时，`operation=null` 明确表示没有可声称已保存的操作。不得手改这些状态制造成功或释放。

**当前格式：**接续要求当前生产者封存的 `object-state.json`；缺失或不匹配就拒绝，不提供历史兼容分支。runner 启动原件生产者、验证器和现役消费者统一采用 digest-only v2。PR 复用现有执行与保留登记；本批没有修改宿主保留政策或共享安装。新增原件 IO、核验和存储的完整成本未测。

查询序号、精确绑定、当前成员替换和接续状态判断直接消费[现有 Verus 证明源码](verus.md#原件交接与定向维护)，
原证明计划与真实 CLI 测试共同验收。证明不替代实际进程原件、GitHub 事实或存储发布核验。

**生产与测试构建配置同改：**PR 两个独立项目的 `profile.dev.opt-level` 均采用 runner 已使用的 `1`，
保留调试断言、未过滤测试、两条测试线程和原业务时限。Cargo 不采用依赖项目自己的 profile；
此前 PR 根项目会把真实 runner 编成未优化版本，并发查询的原回执已出现 5 秒期限耗尽。
此处统一实际开发执行物的优化配置，不另造构建入口；冷构建、运行及总成本须按相同输入分别核验。

scoped worktree 单元中的 PR 行为测试与工作树库存、core／adoption 测试共用现有
`worktree-test-inventory` 资源声明，避免这些活动在同一执行器内重叠。现有调度器负责
互斥，保留原优化、断言、测试线程、时限和其它并发；完整成本未测。发布验证每个作业
独立执行同一未过滤操作。

## 验收与范围

登记的 `test:pr-tests` 执行两项目格式检查及 Rust 行为测试。测试项目直接依赖生产库，并将生产 `src/main.rs` 编译为 `chrono-pr-test-cli`，行为测试通过 Cargo 提供的执行物路径调用它。测试不消费 `crates/pr/target/`，因此计划不再额外执行 `build.pr`；日常 CLI 构建仍使用上文登记入口。两个项目继续保留独立 target。

当前 `test.pr-tests` 保留全部未过滤测试，显式使用 `-- --test-threads=2`；本地、CI 和委托该操作的发布验证共用此入口。该选择降低测试自身并行度以避免 fixture 互相挤占时限，保留所有断言和业务时限；不代表生产延迟改善，完整 CI 成本未测。历史实验和失败背景直接查[引入 PR](https://github.com/ChronoAIProject/chrono-harness/pull/541)及其 Git 历史。测试用独立 Rust gh 替身核实际 argv、stdin、输出和退出状态，覆盖创建／复用、失败恢复、字面文本、身份变化、缺检查、失败检查、截断和协议错误，以及原生等待后的重新核对。gh 替身在执行模拟副作用前核真实 intent 与输入原件；另测持久结果／流、未登记时零派发、结果发布失败和真实合并身份。实际中断测试用单个阻塞 Unix socket 握手，在 gh 尚运行时核启动记录和部分 stdout，再中断其 PR 启动者，由现有执行器加入原任务；维护后保留未知原件且接续查询零派发。该测试只使用已有 `libc` 绑定操作自身进程，不引入新的进程控制实现。接续测试实际跨 CLI 调用，并在诊断期限后执行现有维护，核旧操作连同进程原件回收、当前 OPEN 与其他调用方保留、终态回收及已回收原件拒绝；失败／活生产者／身份变化均保留原保护。外部接口样本独立登记。

PR 测试断言失败时，宿主样本通过固定 tempfile 的调试接口保留现场，并在原 stderr 给出准确路径；成功路径继续自动回收。维护回收断言带最后一次实际维护结果，供同次失败诊断。保留现场由 pr-tests 负责，只用于该次调试及回归验收；义务完成后核对准确对象、活跃使用和必要原件再回收，不按临时目录名或年龄推定可删。此改动只补诊断，不改变原断言、维护轮数、测试线程或时限，完整成本未测。

外层中断回归的提前完成提示只在原握手 socket 写固定的小消息，完整进程结果由原线程的 `join` 交回。
真实握手后，调用方已经转入线程等待，不再读取后续连接；把完整诊断写入该连接会在超过 socket 容量时互相等待。
同一用例增加 64 KiB 环境输入验证大结果仍可完成加入，保留原部分流、启动身份、未知原件和零重派发断言，以及原线程和时限。

并发排序回归用原生 socket 握手确认：等待期间的另一次 API 查询已经实际启动并绑定观察顺序，随后同时放行两条原通道。两项命令分别封存结果，测试加入两项命令后再核对最终对象保管与回收；不把另一命令的完整封存串在原生等待之前。原 5 秒时限、查询次数和结果断言保留。
